# Orchestrator decisions (binding for all agents; read with AGENT_RULES.md)

Each entry answers a design question raised by an agent. DESIGN.md also records the ones that change behavior.

| # | Question (raised by) | Decision |
|---|---|---|
| OD-1 | Byte encodings in tuple hashes (5.3a) | DESIGN section 6, "Encoding rules": 33-byte public keys; raw bytes for hashes, nonces and salts; UTF-8 strings; uppercase hex on the ledger; `pqKeyHash = tupleHash("legx/pq-keyset/v1", ...)`; fixed role strings. |
| OD-2 | The gate's `ONBOARDING_OK` without the salt (1.2) | The gate trusts the client's own lawyer's `identity.onboarded` attestation, which states `C_side`. It does not recompute the commitment. (DESIGN 6.17) |
| OD-3 | Checkpoint key (1.2) | `CheckpointSignerPort`: Ed25519 plus ML-DSA-44. (DESIGN 6.13) |
| OD-4 | FROST slot signer type (1.2) | Slot signers are FROST sessions from `@legx/core/frost`, never `SignerPort`. |
| OD-5 | API authentication (1.2) | Hybrid enrollment-key signature over `tupleHash("legx/api-request/v1", [method, path, SHA-256(body), nonce32, ledgerIndex])`. ML-DSA context `legx/api-request/v1`. The nonce is single use. The ledger index may be at most 20 ledgers old. (DESIGN 8.10) |
| OD-6 | FROST complaint (1.2) | Carries the signed ciphertext and the decrypted share. Anyone checks it against Feldman commitments. The DKG aborts and restarts. (DESIGN 6.4) |
| OD-7 | `RELEASE_ESCROW` in the state machine (1.14) | Single-signed by the sealed releaser. It carries `{gatePassed, submitter, releaser}`. No quorum check. |
| OD-8 | Which path is signed (4.1b) | The URL path plus the query string, exactly as sent (`pathname + search`), without scheme, host or port. |
| OD-9 | The live-feed payload (4.1b) | Each pushed row is `{seq, topic, payload}`. For topic `deal.event`, `payload` is `{envelope: base64 of the exact stored DSSE bytes, summary: {kind, state, ledger?: {tx_hash, ledger_index}}}`. The server also pushes `{topic: "ledger.validated", payload: {index, hash, close_time}}` on every validated ledger it sees. |
| OD-10 | Where clients get the ledger index for signing (4.1b) | From the latest `ledger.validated` push (OD-9). The lawyer console also checks it against its own read-only public XRPL connection (IMPLEMENTATION 4.4). |
| OD-11 | Fee headroom on `AccountDelete` (2.3) | No headroom: its fee is burned. "Exits" with 5 to 10 times the fee means step 8 payments (and dispute exits) only. |
| OD-12 | A struck-off status in the mock registry (3.3a) | The `demo` adapter maps `struck_off` and `lapsed` to `not_active`. |
| OD-13 | `bar_number_sha256` (1.10) | SHA-256 of the normalized bar number's UTF-8 bytes. (DESIGN encoding rules) |
| OD-14 | Envelope payload size under KMS (3.6) | An evidence payload stays at or under 4 KB (the AWS KMS limit for signing raw Ed25519 messages). Larger content (proofs, bundles, documents) is stored in the object store as an attachment, and the payload carries its SHA-256 (`payload_commitment`, DESIGN 8.1). ML-DSA always signs the full PAE through `EXTERNAL_MU`. |
| OD-15 | Collector redaction key (3.6) | The redaction processor's `hmac_key` (32 bytes) comes from an env var; DESIGN 8.6 is updated. |
| OD-16 | FROST complaint verification (1.15) | A complaint reveals the complainant's per-holder session decryption key for that DKG only, so anyone can decrypt the signed ciphertext and verify the share. This supersedes the "decrypted share only" part of OD-6. |
| OD-17 | Role names (1.15) | `phone`, `second-authenticator`, `recovery-agent`, `console`, `firm-hsm`, `partner`, as in DESIGN 6.4. Never `security-key`. |
| OD-18 | Recovery proof window (1.15) | A recovery request's fresh ZK proof must be no older than 10 minutes by ledger time when the recovery starts. The 72-hour delay follows. |
| OD-19 | New tags (1.16) | Confirmed: `legx/renewal/v1`, `legx/renewal-statement/v1`, `legx/hpke/backup/v1`, `legx/hpke/share/v1`. Every new tag must be added to the tag list in the agent's status file. The audit wave checks them for uniqueness. |
| OD-20 | Signed-note format (1.16) | The C2SP signature line begins with the em dash character, as the spec requires. That is a protocol literal, not prose, so the "no em dash" writing rule does not apply to it. |
| OD-21 | Binding attestation signers to the seal (1.9) | An attestation (passport, onboarding, gate record) is accepted only if it is hybrid-signed by an enrollment key of the right lawyer slot, AND that key's ML-DSA-65 public key is one of the three keys behind the sealed `pqKeyHash` of that slot. No extra FROST signature. |
| OD-22 | Where chip authentication is enforced (1.9) | The lawyer's console records `chip_auth_available` (DG14 or DG15 present) in the `nfc-chip` checks. `verifyAttestation` refuses `chip_authentication: "none"` when it is true. |
| OD-23 | Active or Chip Authentication (1.9) | A chip with DG15 must use Active Authentication, whose challenge is the first 8 bytes of `presenceMsg`. Chip Authentication alone is accepted only when DG15 is absent. That is weaker, because it is not bound to `presenceMsg`, and it is recorded so. |
| OD-24 | noble ML-DSA reachable from services (3.12) | Accepted for verification only: verification uses public data, so constant-time concerns do not apply. Servers must never call noble's sign or keygen. A test pins that, and the biome rule stays for direct imports. |
| OD-25 | Storing the full ZK proof set (3.11, 1.17) | The public proofs go in `zk_proof`. The disclosure proof (names in clear) is stored as an attachment encrypted to the client's own lawyer (X-Wing, kind `zk-disclosure`). Re-verification opens it with the lawyer's key, or uses only the public proofs when the disclosed facts are not needed. |
| OD-26 | Recovery-code mode (4.2) | Labeled "single-device mode" unless the user confirms the recovery code is kept off the phone (on paper, or on another device). The UI asks, and records the answer in the vault metadata. |
| OD-27 | Browser safety of `@legx/core` (4.2) | `@legx/core` must run in browsers: no `Buffer`, `node:*` imports or other Node-only globals in `src/`. Use `Uint8Array` with the `@noble/hashes` and `@scure/base` helpers. A lint rule and a browser smoke test enforce it. |
| OD-28 | The release code when lawyer B is replaced before release (2.5) | The old lawyer B hands the 32-byte release code to the new lawyer B, encrypted with X-Wing HPKE (kind `release-code-handover`), as a logged evidence event (code never in clear outside the two consoles). If the old lawyer B is unavailable, the quarantine escrow is left to expire at `CancelAfter` (refund to Alice), and the new lawyer B makes a new code and condition for a new escrow. |
| OD-29 | `IDS_DISTINCT` with salted commitments (E2E-P1, I-E4) | Each `identity.onboarded` attestation also carries `distinct_tag = tupleHash("legx/id-distinct/v1", [utf8(dealId), X])`, where X is `utf8(N_side)` for `zkpassport`, or `SHA-256(DG1)` for `nfc-chip`. The gate requires `distinct_tag_A != distinct_tag_B`. The tag links only within one deal. |
| OD-30 | Unsigned `/health` (3.7) | Accepted: `/health` is unsigned and shows only each port's name, profile and ok/fail state, never data or keys. |
| OD-31 | Projector dashboard authentication (4.5) | The dashboard holds its own pinned `observer` enrollment key (hybrid), registered like any holder key (6.3). The `observer` role may only subscribe to the live feed and call read routes. It can never sign or post. In the demo profile, the key is made at seeding. |
| OD-32 | Where onboarding ZK verification runs (4.8 DQ1) | In the client's own lawyer's console, which opens the `zk-disclosure` box (OD-25) and then signs `identity.onboarded` (OD-2). The server's ZK route verifies only the public proofs, and never receives the disclosure box in clear. |
| OD-33 | Where the client's own account key lives for badge acceptance (step 5f, F4) | The client's XRPL account IS the slot account: its key is the slot's FROST group key (6.4). Step 5f `CredentialAccept` is signed single-signed by the client's FROST pair (phone plus second-authenticator). The signer allow-list gains one entry: `CredentialAccept` with `Account` = this slot's account, `Issuer` = the sealed deal wallet and `CredentialType` = the sealed type, with no other fields. There is no separate account key. |
| OD-34 | `face_match_passed` when no face match runs (I-DOC-1, I-2.9-f) | The field is always the honest result: true only if a strict face match was verified (the console's `facematchMode === 'strict'` is right). The production gate requires true for `zkpassport` release. Only the demo profile, which already needs `devMode`, may accept false, and records it as a `DEMO_NO_FACE_MATCH` warning in the gate record. The 2.9 headless flow must record false, not true. |
| OD-35 | Which key the lawyer console uses to list its deals (I-W-10) | Enrollment keys stay per deal and role (4.9), so no long-lived key links one lawyer's deals together. The console lists the deals it holds keys for from vault metadata. For each one, it calls `deals.mine` signed with that deal's console enrollment key, to get the role and state. There is no directory key for listing. |
| OD-36 | Seal source for vault frames, and the route for the salt and disclosure box (R2-web) | (a) The vault frame never trusts a seal it is handed. It fetches `/deals/:id/public-data` itself, recomputes `dealSeal` with `@legx/core/dealcore`, and signs only if that equals the seal pinned in vault metadata at join time. (b) The client's salt and the ZK disclosure proof go to their own lawyer only as X-Wing boxes (kinds `zk-disclosure`, OD-25). The coordinator stores each as an attachment, and serves it with a read route (`GET /deals/:id/identity-box/:side`) only to that side's lawyer console enrollment key (holder role `console`). The server never sees plaintext. |
