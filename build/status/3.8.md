## What it checks (DESIGN 8.8)
`manifest` (SHA-256 and size of every file; extra and missing files), `manifest-signature` (service hybrid DSSE over the manifest digest; pin with `--service-key`, otherwise a warning that the key is the bundle's own), `hybrid-signature` (both signatures of every event, ed25519 then ML-DSA-65), `chain` (seq, prev_hash, file name), `checkpoint` (both lines 0x01 and 0x06, vkeys), `merkle-proof` (every `.tlog-proof` against the checkpoint root), `consistency`, `anchor` (recorded raw ledger JSON from each server: hash, ledger index, `tesSUCCESS`, memo carries tree size, root and origin hash; servers agree), `timestamp` (RFC 3161 tokens over the checkpoint, chain to `timestamps/roots.pem`), `contract` and `clause-proof`, `attestation` (hybrid signatures of `attestations/` and `release/gate/`), `trust-profile`, `zk-proof` (offline re-verification), `signed-contract`, `bindings`, `bar-records`, `attestations`, `release-gate` (all from the rerun of `checkRelease`), and the optional separate step `chain-check (ONLINE, optional)` (`--chain-check --rpc-url`, compares recorded registry `eth_call` answers with a live node; the only code that uses `fetch`).
Exit codes: 0 pass; 1 any failure (the report line is `FAIL  <file>  [<check>]  <reason>`); 2 wrong usage. Reports: text on stdout and `legx-verify-report.txt` / `.json` in `--out-dir`. A check that cannot run because the bundle lacks data is `SKIP` ("not verified"); `--require-complete` makes it a failure.

## Evidence for deviations
- esbuild instead of a hand-made bundle: `scripts/bundle.ts`. Two things needed: `ws` (xrpl network client) is aliased to a stub so no socket/HTTP/TLS code enters the file; `packages/zk/src/sdk.ts` loads the SDK with `createRequire`, which a bundler cannot follow, so the build plugin swaps it for a plain `require('@zkpassport/sdk')` that esbuild inlines. The bare-folder test found the first problem (a missing module at run time).
- barretenberg is a native 20 MB `bb` program (via `@aztec/bb.js`, Unix socket plus `child_process`), so ZK re-verification cannot be inside one JS file. DESIGN 8.8 item 12 is therefore met for everything except ZK proofs: ship `bb` next to `verify.js` and run `--bb`. Without it the proofs are reported "not verified" (not "passed").
- A genuine bug in task 3.4 was found by the one-byte test (time-stamp signature ignored); see ISSUES.md 1 and 2. Worked around in `src/log.ts` (`cmsSignatureValid`).

## Design questions
- DQ-3.8-1: with no pinned key the manifest signature and the checkpoint keys are trusted from the bundle itself. The real anchors of trust are the ledger anchor and the time stamps. Should the evidence service print the service and checkpoint key fingerprints somewhere an arbitrator gets out of band (the FRE 902 template)? The CLI has `--service-key` only.

## Known gaps
- Item 8 (signed contract), 9 (bindings, bar) and 10 (attestations) are verified only through the gate rerun, so only when `release/gate-input.json` exists (the builder does not write it yet). The attestation/gate-record signatures (`attestation` check) are verified from the files that exist today, but not tested on real attestation envelopes (the evidence test world has none).
- ZK re-verification, trust-profile and gate rerun are tested with fixtures (task 1.17 sets, task 1.12 world) placed in the bundle by the tests, not with files from the real builder.
- Event ledger links (`predicate.ledger`) are not re-checked offline except through the anchor and release transactions.
- Key validity is judged at the event's own signed `occurred_at` (the bundle holds no clock).
- Windows/Linux not run; the `bb` path in bundle.test is macOS/Linux x64/arm64 only.
