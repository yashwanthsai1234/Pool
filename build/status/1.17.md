## Research notes
- **[CHECK] API, pinned by `zk/test/request.test.ts` against SDK 0.19.2 `createQuery()`:**
  - expiry: `.gt("expiry_date", Date)` gives `{expiry_date:{gt:ISO}}`;
  - face match: `.facematch("strict")` gives `{facematch:{mode:"strict"}}` (the default mode is also "strict");
  - bound value: `.bind("custom_data", v)`.
  - Source: the SDK `dist/esm/index-D9GMXc4k.d.ts` QueryBuilder.
- **Verify config:** `verify({config})` passes `config` whole to `createRegistryClient(chain, config)` (bundle `index.cjs`). So `rpcUrl`, `circuitManifestUrlGenerator`, `packagedCircuitUrlGenerator`, `packagedCertsUrlGenerator` and `sanctionsTreeUrlGenerator` all work, although the SDK's `VerificationConfig` type declares only `rpcUrl`. Source: the `RegistryClientOptions` typing in registry 0.15.3.
- **Root check:** the call is `isRootValid(bytes32 registryId, bytes32 root, uint256 timestamp)`, selector `0x2aae4296`. The timestamp is the proof date, so the call data is deterministic and can be replayed. The SDK sends it with `"latest"`; the recorder pins it to a block. Source: `registry-sdk/src/client.ts` at a61b0cf.
- **Date check:** `checkCurrentDate` counts from local midnight. Offline re-verification shifts `validity` by the whole days since recording (`loaders.verifiedDay`), so every proof keeps the verdict it had when recorded.
- **Expiry granularity:** `getExpiryDateCircuitInputs` adds 1 day for `gt` (circuit bounds are inclusive, whole days). Source: `circuit-matcher.ts`.
- **Face match:** verify requires a facematch proof with an App Attest or Play Integrity root, `environment === "production"` and ZKPassport's app ID. No headless prover can make one. So the recorded release has the face match off, and a separate fixture records the failure (`facematch.commitment`).
- **Sockets:** bb.js talks to its native prover over a Unix socket. The offline test therefore blocks only TCP.
- **Prototype facts confirmed in the recording (24 Oct 2026):**
  - the identifier is the same for onboarding and release (same passport, domain and scope);
  - it differs for a second passport, a second scope and a second domain;
  - type `NON_SALTED_MOCK` (2);
  - about 20 s per proof set on this machine, under load; verify takes 0.6 to 0.8 s.

## Evidence (deviations from the plan)
1. **Fixtures live in `packages/zk/fixtures/`, and the tools in `packages/zk/tools/`.** The prompt says so; IMPLEMENTATION 1.17 said `packages/fixtures/zk/` and `tools/record-zk/`. Task 1.17 owns only `packages/zk`.
2. **`proofSha256` hashes the public proof set.** The full onboarding set carries the disclosed name and birth-date bytes in clear in `committedInputs.disclose_bytes` (a test shows the bytes `65,76,73,67,69` = "ALICE" are there). `publicProofSet` drops them, and `proofSha256` = SHA-256 of `JSON.stringify(publicProofSet(proofs))`, which is what the evidence log stores. The full set is needed only to re-verify onboarding; its disclose inputs belong in the lawyer's box.
3. **Production refusal order follows task 1.9's `checkTrustRecord`:** dev mode, then Sepolia, then mock. The recorded mock proofs therefore report `DEVMODE_REFUSED` in production. Every single-fault case still reports its own code.
4. **`EXPIRY_TOO_EARLY` rule:** the stored `expiry_date.gt` X must be at least CancelAfter + 30 days.
   - `gt` proves expiry > X, so the tightest bound a document expiring at E can prove is X = E − 1 s.
   - So E = CA + 30 d + 1 s passes and E = CA + 30 d fails, which matches the row.
   - The request builder uses X = CA + 30 d exactly, and that passes.
5. **The SDK throws on malformed proof sets** (for example, a missing `committedInputs`) → `reverifyOffline` returns `PROOF_NOT_VERIFIED`.
6. **Sandboxes are in `build/tmp/1.17/`:**
   - `sbx1.ts` proves and verifies the onboarding query with the vendored prover: `verified: true`, after the birth-date fix;
   - `sbx2.ts` shows that verify opens Unix-socket connections only, and that the RPC call data is identical across runs;
   - `sbx3.ts` shows that the contracts `ZkProof` rejects `committedInputs` (`Unrecognized key: "committedInputs"`);
   - `record.summary.log` is the recorder's output.
7. **The vendored prover (`tools/zk-prove/prove.ts`)** comes from upstream commit a61b0cf (Apache-2.0, `LICENSE` copied from the SDK package of the same commit). Five changes are marked `legx:`:

## Design questions
1. **The prompt says "T-U-28 (a to n per IMPLEMENTATION)", but IMPLEMENTATION defines only T-U-28a to c.** I built a to c, plus P1.17-01 to 20.
2. **Who stores the full onboarding proof set?** An arbitrator re-verifying onboarding needs the `disclose_bytes` committed inputs, which reveal the disclosed facts. Proposal: put them in the disclosure box sealed to the lawyer, so the lawyer supplies them in a dispute. `publicProofSet` and the box functions support this; the onboarding flow (tasks 4.4 and 4.8) decides.
3. **The face match cannot be tested end to end without the app.** The release rule is tested with a recorded failure and with a query that has no face match; a passing face match needs one real-app recording (alongside T-U-28c).
4. **The disclose proof's `committedInputs` hold the disclosed bytes in clear.** Should the onboarding QR request disclose at all, or should the facts reach the lawyer only through the app's result? Today, DESIGN says disclose.
