## What was built
- `tools/release-hash`: `manifest.ts` (sorted file hashes, manifest hash, SRI injection), `release.ts` (zod body, canonical message, `signRelease` through any `SignerPort`, `verifyRelease` in the browser with both signatures), `build.ts` (`hashDir`, `writeRelease`), `cli.ts` (`keygen`, `sign`; keys are PEM, signing uses `nodeSigner`), `Dockerfile.build`.
- `apps/vault-host`: `vite.config.ts` (reproducible settings, commented), `src/frame.ts` (self-check, then `serveVault`), `check.ts`, `schema.ts`, `app.ts` (`connectVaultFrame`, pinned origin, `VAULT_FRAME_ALLOW`), `headers.ts` (CSP from `VAULT_CSP`, `_headers`), `scripts/build.ts`.
- Flow: the page loads one script (SRI plus CSP hash). It fetches `release.json` from the release host, verifies Ed25519 and ML-DSA-65 with keys baked into the bundle, fetches every file of the release from its own origin, compares SHA-256, and only then creates the vault. `appOrigin` comes from the signed release.
- Vite: base `./`, no sourcemaps, `codeSplitting: false`, content-hashed names, no asset inlining, no preload. Evidence: two builds identical (test).

## Research notes
URLs in each `SOURCES.md`. A hash in `script-src` matches an external script only with a matching `integrity` (MDN, WPT script-src-sri_hash). Both Chromium and WebKit enforce it here (tests). The web search found no Vite 8 doc on reproducibility; the settings were proved by the test.

## Design questions
- DQ-4.10-a: the self-check needs `connect-src 'self' <release host>`, not `'none'` as in 4.2's `VAULT_CSP`. Code that ran inside the frame could send data to those two hosts. Accepted; to be added to DESIGN 6.4 with the limit text (whoever controls the vault origin can replace the check too).
- DQ-4.10-b: `xrpl` pulls a 2.1 MB `mpt_crypto.wasm` into the bundle. It is hashed and checked, but if ever instantiated the CSP would need `'wasm-unsafe-eval'`. Stubbing it out needs a decision.
