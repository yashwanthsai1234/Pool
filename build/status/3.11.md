## What was built
- `src/config.ts`: start-up checks (domain `legx.app`, devMode refused in production, pinned and installed SDK version, at least two RPC hosts in production, the hosted verifier named anywhere is refused).
- `src/guard.ts`: during a verification the global fetch reaches only the RPC hosts and the circuit hosts; anything else (the hosted verifier above all) throws `ZK_EGRESS_BLOCKED`. A failed or non-2xx answer is recorded as CDN or registry failure. This is needed because the SDK swallows a failed registry read and reports `verified: false` (`checkRegistryRoot`), and `verifyAndRecord` would accept a 503 body as a circuit file.
- `src/adapter.ts`: `createZkAdapter` is a `ZkVerifierPort` over 1.17's `verifyAndRecord`. The first RPC records; every other provider must give the same chain, block hash and `eth_call` answers (`ZK_ROOTS_DISAGREE`, not retried). Core's `checkTrustRecord` applies the profile rules to the result.
- `src/retry.ts`: exponential backoff (3 tries, 250 ms base), only for `ZK_CDN_UNAVAILABLE` (`name: "ZkCdnUnavailable"`) and `ZK_REGISTRY_UNAVAILABLE`.
- `src/store.ts`: `verifyAndStore` (adapter, then core `checkZkResult`, then the object store and `zkProofs.insert`; nothing is written unless all pass) and `reverifyStored` (reads the files back from the object store, each checked against its recorded hash, then 1.17's `reverifyOffline`). Files are content-addressed (`zk/files/<sha256>`, `zk/loaders/<sha256>`); their hashes are in `registry_roots.loader_files`, which the db schema already allowed.

## Design questions
1. `zk_proof.proof` holds the public proof set only (1.17 decision). Re-verifying onboarding needs the disclosed bytes and the original query and query result, so `reverifyStored` takes the proof set from the caller (the bundle). Who keeps the full set for the arbitrator is the open question 2 of 1.17.
2. The SDK prints `console.warn` on a failed registry read. It prints no passport data in what I saw (the scan passes), but the service entry point should route SDK console output to the redacting logger.

## Known gaps
- The adapter serialises verifications (one at a time, as `verifyAndRecord` does, because the SDK reads the global fetch).
- The production refusal of a verified Sepolia or mock record cannot be reached with the mock fixtures through the adapter (devMode is refused first); it is tested through `reverifyStored` and by core's own tests.
