## API
- `@legx/core/attest` (imports no passport parser):
  - `presenceMsg(dealSeal, side, ledgerHash, lawyerNonce)`. It throws `RangeError('NONCE_LENGTH')` when the nonce is not 32 bytes.
  - `checkFreshNonce(nonce, usedSet)` returns `NONCE_REUSED` or `NONCE_LENGTH`. The set holds lowercase hex.
  - `attestConfig({ maxAgeSeconds })`: the default is 3600. It throws `FRESHNESS_LIMIT_TOO_HIGH` above 86400 and `FRESHNESS_LIMIT_INVALID` when the value is not a positive integer.
  - `verifyAttestation({ envelope, side, deal: { id, data: PublicDealData }, sealedKeys: { lawyerKeyIds: { A, B }, registry }, ledgerLookup, now, config?, profile?, zkProof? })` returns `{ ok, method } | { ok: false, code }`. It never throws.
  - `verifyOnboarding({ envelope, side, deal, sealedKeys, now, profile? })` checks the `identity.onboarded` record.
  - `checkTrustRecord(trust, profile)` is shared with task 1.17.
  - Rule order, with the first failure reported: payloadType → hybrid envelope (Ed25519 + ML-DSA-65, keys valid at `now`) → payload shape (`PAYLOAD_MALFORMED`, `NONCE_LENGTH`) → `WRONG_SIGNER` (both key IDs belong to the client's own lawyer, and `checked_by_role` matches) → `WRONG_SIDE` → `DEAL_INVALID` / `WRONG_DEAL` → `COMMITMENT_MISMATCH` → `METHOD_UNKNOWN` / `METHOD_NOT_ALLOWED` / `METHOD_MISMATCH` → `CHECKS_SHAPE_WRONG` → `PRESENCE_MISSING` / `PRESENCE_INVALID` (strict, under the sealed `xPub_side`) → `ANCHOR_UNKNOWN` / `ANCHOR_MISMATCH` → `STALE` → the method's rules (`CHECK_FALSE:<name>`; for zkpassport also `ZK_RECORD_INCOMPLETE`, `DEVMODE_REFUSED`, `SEPOLIA_REFUSED`, `MOCK_IDENTIFIER_REFUSED`, `PROOF_MISSING`, `PROOF_HASH_MISMATCH`).
  - The profile defaults to `production`.
- `@legx/core/passport/passiveAuth`:
  - `passiveAuth({ dg1, sod, dg14?, dg15?, trustList, atTime })` (async; `atTime` is the ledger close_time in Ripple epoch seconds) returns `{ ok, listed, dateOfExpiry }` or a code. ## Research notes
- **ICAO 9303 Part 11** (https://www.icao.int/sites/default/files/publications/DocSeries/9303_p11_cons_en.pdf; I read the PDF text):
  - 5.1.1 lists the inspection steps: read the SOD, which must hold the DS certificate; build the path from the trust anchor to the DS; verify the SOD signature with the DS key; hash the data groups. The best practices are to check the DS key usage and the DocumentTypeExtension, and to keep country codes consistent.
  - 6.1.2.1: RND.IFD MUST be 8 bytes, and nonces MUST NOT be reused.
  - 6.1.2.2 (RSA): ISO/IEC 9796-2 scheme 1. Trailer option 1 (`BC`) is used only for SHA-1. Option 2 uses `38CC` for SHA-224, `34CC` for SHA-256, `36CC` for SHA-384 and `35CC` for SHA-512. M1 has c − 4 bits with c = k − Lh − 8t − 4, and σ does not contain M2.
  - 6.1.2.3 (ECDSA): the TR-03111 plain format over RND.IFD. SHA-1 and RIPEMD-160 SHALL NOT be used.
  - Appendix F has a worked RSA-1024/SHA-1 example. It gives F, M1, M2 and S but no modulus, so I test the representative check on its F (`iso9796d2Recovers`).
- **BSI TR-03105-5 reference data set** (https://www.bsi.bund.de/SharedDocs/Downloads/DE/BSI/Publikationen/TechnischeRichtlinien/TR03105/BSI_TR-03105-5_ReferenceDataSet_zip.zip, zip SHA-256 `2854003b…d21c`):
  - It contains `DG15_sk.pkcs8`, a 1024-bit RSA Active Authentication key, with the matching `Datagroup15.bin`.
  - Its `EF_SOD.bin` has an RSA-PSS DS and NULL digest parameters, and lists DG 1, 2, 3, 4 and 14. DG15 is not listed.
  - `Datagroup14.bin` holds Chip Authentication data only, with an explicit brainpoolP224r1-sized curve.
  - I copied the 5 small files into `packages/core/test/passport/data/bsi-tr03105-5/`.
  - The data set has no CSCA, so the test checks that the SOD signature verifies and that the chain then fails `DS_NOT_CHAINED`.
- **ISO/IEC 9796-2** (https://www.iso.org/standard/54788.html, paywalled). I used BouncyCastle `ISO9796d2Signer.verifySignature` (https://github.com/bcgit/bc-java/blob/main/core/src/main/java/org/bouncycastle/crypto/signers/ISO9796d2Signer.java) as the readable reference:
  - the header bits are `01` and the "more data" bit is 1 for partial recovery;
  - padding is `B` nibbles closed by an `A` nibble;
  - if J mod 16 ≠ 12, use n − J.
- **PKI.js 3.4.3** (read in `node_modules` and on GitHub at tag v3.4.3):
  - `SignedData.verify` compares the messageDigest attribute and then verifies `signedAttrs.encodedValue`, which `SignedAndUnsignedAttributes` re-tags from `[0]` to `0x31` (src/SignedAndUnsignedAttributes.ts lines 148 to 152).
  - `CryptoEngine.verifyWithPublicKey` (src/CryptoEngine/CryptoEngine.ts line 1914) converts ECDSA DER to the WebCrypto form and handles RSA-PSS parameters.
  - It does not check that the contentType attribute equals eContentType, so we do.
  - Sandbox (an inline script, deleted after use) on the fixture and BSI SODs printed: `good sig true`, `badSodSignature false`, `brainpoolDs threw Unsupported algorithm identifier : 1.3.36.3.3.2.8.1.1.7`, `highS true` (WebCrypto accepts high S), `bsi sig true 1.2.840.113549.1.1.10`, and `rsapss true`.
- **noble v2 and lowS**: `build/tmp/1.9/lows.ts` printed `lowS true false` and `lowS false true` for a high-S P-256 signature. Every passport ECDSA check in noble passes `lowS: false`, and the mutation check above confirms the tests depend on it.
- **asn1js depth**: `build/tmp/1.9/deep-sandbox.ts`. 20,000 nested indefinite-length SEQUENCEs do not throw and are refused. A test now covers this.

## Evidence (deviations and additions)
1. **SOD signature before the chain.** ICAO lists the chain (step 2) before the signature (step 3). Both are mandatory, so the order changes only which code is reported. Checking the signature first lets the BSI sample, which has no CSCA, still exercise our RSA-PSS SOD signature check.
2. **noble is used for more than brainpool.** It also covers EC keys with explicit domain parameters, which are common on real CSCAs and chips. The parameters are matched against the noble curves by p, a, b, G and n. WebCrypto and PKI.js reject such keys (`Incorrect type for ECDSA public key parameters`). The test is a DG15 with explicit P-256 parameters.
3. **More reason codes than IMPLEMENTATION lists**, so each failure has its own name: `WRONG_SIDE`, `DEAL_INVALID`, `ANCHOR_UNKNOWN`, `PAYLOAD_MALFORMED`, `ENVELOPE_INVALID:<hybrid code>`, `CSCA_EXPIRED`, `DG15_MISSING`, `PROOF_MISSING`, and the passiveAuth and AA codes. Where task 1.8's fixture suggestions existed, I used them unchanged.
4. **One redundant check removed from `chipChecks`.** An AA answer without DG15 listed in the SOD can never pass, because `passiveAuth` already fails a supplied DG15 that is not listed, and a missing DG15 gives `DG15_MISSING`.
5. **The `verifyAttestation` input has more fields than the IMPLEMENTATION sketch** (`{ envelope, deal, sealedKeys, ledgerLookup, now }`). It also takes:
   - `side`, because the gate asks per side;
   - `config`, the freshness limit, built only by `attestConfig`;
   - `profile`, production or demo, as an input and not a global (IMPLEMENTATION 1.12);
   - `zkProof`, the stored proof bytes for the `proof_sha256` check.

## Design questions
1. **Which key is "the client's own lawyer key" on an attestation?**
   - I verify the attestation as a hybrid DSSE envelope (DESIGN 8.1, 6.13). Both key IDs must be among the lawyer's enrollment key IDs for that side, which the caller supplies from the pinned key directory (`sealedKeys.lawyerKeyIds`).
   - DESIGN 10.1 says "that side's own sealed lawyer key". `lawyerPub_side` in the seal is a FROST group key, and DESIGN gives the attestation no FROST signature (unlike `release.gate.passed`).
   - Should the gate also check that the ML-DSA key is one of the three hashed into `pqKeyHash_L*`, or should attestations carry a lawyer-slot FROST signature? I followed 8.1 and left both open.
2. **`CHIP_AUTH_REQUIRED` cannot be enforced by `verifyAttestation`.** It never sees the chip's file list (I7). The rule lives in `chipChecks` on the lawyer's console, and the gate trusts the lawyer's `chip_authentication` value (D21).
3. **Chip Authentication binding [CHECK].**
   - `chipChecks` accepts `caPassed` from the native reader only when the SOD lists DG14, and it records `"CA"`. CA is not bound to `presenceMsg`, so a relayed chip could pass CA in another session.
   - If the SOD lists DG15 and an AA answer is given, it must verify. A DG15 chip with only `caPassed` is still recorded as `"CA"`.
   - Should DG15 chips be forced to use AA? Many EU passports (for example DE) have only CA, so forcing AA would block them.

## Known gaps
- No CRL or revocation check for DS and CSCA certificates. The ICAO PKD and master-list sourcing is O10.
- Unknown critical extensions are not rejected.
- Two Part 11 best-practice checks are not done: DocumentTypeExtension consistency and country-code consistency.
- DG1 must be a TD3 passport MRZ; ID-card TD1 and TD2 are refused. Expiry years are read as 20YY.
- RSA AA needs a signature of exactly the modulus length.
- Curves without a noble implementation are refused as unsupported: P-224, brainpoolP224r1, and P-192.
- The subject-key-identifier `sid` path in `parseSod` has no test, because the fixtures use `issuerAndSerialNumber`.
- `JSON.parse` takes the last of any duplicate keys in a signed payload. The lawyer signed those exact bytes, so another verifier in a different language could read them differently; no canonical-JSON check is done.
- If a caller's `ledgerLookup` throws, the result is reported as `PAYLOAD_MALFORMED`.
