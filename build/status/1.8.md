## API (`@legx/fixtures`, see `src/index.ts`)

- `makeTestPki({ seed, alg? })` returns `{ alg, csca: { cert, key }, ds: { cert, key } }`. `alg` is `'ecdsa-p256'` (the default) or `'rsa-pss'`.
- `makePassport({ pki, mrz, seed, aa? })` returns `{ mrz, dg1, dg14?, dg15, sod, aaKey }`.
  - `aa` is `'ec'` (the default: P-256, and DG14 with ecdsa-plain-SHA256), `'rsa'` (2048-bit, ISO 9796-2 with SHA-256), or `'none'`. With `'none'` there is no DG15 and the SOD has 1 hash, which is invalid.
  - The overloads type `dg15` and `aaKey` as present when `aa` is not `'none'`.
- `chipAnswerAA(aaKey, challenge8)`: an EC key gives a 64-byte `r||s` over SHA-256(challenge). An RSA key gives an ISO/IEC 9796-2 scheme 1 signature with partial recovery: `6A || M1 || SHA-256(M1||M2) || 34CC`, with M1 derived from the key and the challenge.
- `makeBadVariants({ pki, mrz, seed })` returns one entry per variant, each `{ name, passport, expect, reason, description }`:

  | Variant | Expected | Reason code / note |
  |---|---|---|
  | `badSodSignature` | reject | `SOD_SIGNATURE_INVALID` |
  | `wrongCsca` | reject | `DS_NOT_CHAINED`. Also returns `rogueCsca`. |
  | `changedDg1` | reject | `DG1_HASH_MISMATCH` |
  | `expiredDocument` | reject | `DOCUMENT_EXPIRED` |
  | `expiredDsCert` | reject | `DS_EXPIRED` |
  | `singleHash` | reject | `LDS_TOO_FEW_HASHES` |
  | `messageDigestMismatch` | reject | `SOD_DIGEST_MISMATCH` |
  | `wrongContentType` | reject | `SOD_CONTENT_TYPE` |
  | `noDsCertificate` | reject | `DS_CERT_MISSING` |
  | `dsKeyUsage` | reject | `DS_KEY_USAGE` |
  | `changedDg15` | reject | `DG15_HASH_MISMATCH` |
  | `badCheckDigit` | reject | `MRZ_CHECK_DIGIT` |
  | `brainpoolDs` | accept | Needs the noble fallback. |
  | `highS` | accept | ECDSA only. Verify with `lowS: false`. |

  That is 12 reject variants and 2 valid but unusual ones. For a P-256 PKI the factory returns all 14. For an RSA-PSS PKI it returns 13, because `highS` does not apply.
- `parseSod(bytes)` and `parseDg1(bytes)` return a `Parsed<T>` (`{ ok, value } | { ok: false, error }`) and never throw.
- `DEMO_NAMES` and `demoPassport(name)` rebuild the demo passports from fixed seeds, including their AA keys. The demo JSON files hold public data only.

## Research notes

- **ICAO 9303 Part 10** (https://www.icao.int/sites/default/files/publications/DocSeries/9303_p10_cons_en.pdf):
  - EF.SOD is tag `77`.
  - LDSSecurityObject is defined in 4.6.2.3: `dataGroupHashValues SEQUENCE SIZE (2..ub-DataGroups)` with ub = 16. The `ldsVersionInfo` field is present if and only if the version is v1.
  - Table 37 is the SignedData profile: v3, the DS certificate REQUIRED, one SignerInfo recommended, issuerAndSerialNumber recommended, signedAttrs mandatory.
  - Note 2 of 4.6.2.3: DigestAlgorithmIdentifiers MUST omit NULL. I checked our output with `openssl asn1parse`: the digest AlgorithmIdentifier is 11 bytes with no NULL.
- **ICAO 9303 Part 11** (https://www.icao.int/sites/default/files/publications/DocSeries/9303_p11_cons_en.pdf):
  - 6.1.2.1: RND.IFD MUST be 8 bytes.
  - 6.1.2.2 (RSA): ISO/IEC 9796-2 scheme 1, with M1 of c - 4 bits where c = k - Lh - 8t - 4. The trailer is BC (SHA-1) or 34CC (SHA-256).
  - 6.1.2.3 (ECDSA): the plain format from TR-03111, signed over the message RND.IFD.
  - 9.2.4: DG14 MUST hold ActiveAuthenticationInfo when Active Authentication uses ECDSA. This is why the EC fixtures carry DG14.
  - 6.1.5: DG15 holds a SubjectPublicKeyInfo.
- **ICAO 9303 Part 12** (https://www.icao.int/sites/default/files/publications/DocSeries/9303_p12_cons_en.pdf):
  - Table 1 (validity): CSCA 13 to 15 years, private key use 3 to 5 years; DS about 10 years, private key use up to 3 months.
  - Table 5 (fields): v3; a positive serial of at most 20 octets; PrintableString countryName that matches between issuer and subject; UTCTime with seconds.
  - Table 6 (extensions):
    - CSCA: SKI, KU (critical, keyCertSign and cRLSign), PKUP, SAN, IAN, basicConstraints (critical, cA, pathLen 0), CRLDP.
    - DS: AKI, KU (critical, digitalSignature), PKUP, SAN, IAN, CRLDP, and documentTypeList (2.23.136.1.1.6.2, not critical, holding `P`).
  - 7.1.1.2: the altName is a directoryName with only `L=<MRZ country code>`.
  - Our certificates implement all of this. The CRLDP points to `https://legx-demo.invalid/...`, so it never names a real ICAO URL.
- **BSI TR-03111**: ecdsa-plain-SHA256 is 0.4.0.127.0.7.1.1.4.1.3. Sources: https://www.bsi.bund.de/SharedDocs/Downloads/EN/BSI/Publications/TechGuidelines/TR03111/BSI-TR-03111_V-2-1_pdf.pdf?__blob=publicationFile and the BouncyCastle BSIObjectIdentifiers javadoc.
- **ISO/IEC 9796-2 representative layout**: header `6A` for partial recovery, then M1, then H, then the trailer. I followed BouncyCastle `ISO9796d2Signer.generateSignature` (https://github.com/bcgit/bc-java/blob/main/core/src/main/java/org/bouncycastle/crypto/signers/ISO9796d2Signer.java). The chip returns sigma = F^d mod n, not min(sigma, n - sigma).
- **Libraries**: the versions match IMPLEMENTATION 4.6 and the research notes (`r4-crypto.md`).
  - `pkijs` 3.4.3 with `asn1js` 3.1.0 (PKI.js 4 needs asn1js 4).
  - `@peculiar/asn1-*` 2.11.0. Note: `IssueAlternativeName` is the class's real, misspelled name in asn1-x509 2.11.0.
  - `@noble/curves` and `@noble/hashes` 2.4.0. Brainpool comes from `@noble/curves/misc.js`. noble signs with low S by default, so `highS` is made explicitly.
  - `mrz` 5.0.2, used as an independent validator. It rejects `UTO`, so the fixtures use `XXA`.
  - `@li0ard/tsemrtd` 0.3.5. Its LDSObject schema has no `ldsVersionInfo`, but it still parses our v1 SOD, because asn1-schema ignores the extra trailing field.
- **OpenSSL** re-encodes signed attributes before checking the signature (RFC 5652 5.4), so we DER-sort the SET OF (X.690 11.6) in `derSetOf`.

## Evidence (deviations from IMPLEMENTATION 1.8)

1. **Certificates are built with `@peculiar/asn1-x509` and signed with noble, not with `@peculiar/x509`.**
   - Why: IMPLEMENTATION requires every fixture to be deterministic. `@peculiar/x509`'s `X509CertificateGenerator` signs through WebCrypto (`crypto.subtle.sign`, build `x509.es.js` line 3161), and WebCrypto ECDSA uses a random nonce.
   - Sandbox `build/tmp/1.8/sandbox1.ts` (run with `node build/tmp/1.8/sandbox1.ts`) printed `noble deterministic true 64` and `webcrypto ECDSA deterministic false`.
   - `@peculiar/x509` also pulls in `tsyringe` and needs the `reflect-metadata` global.
   - noble uses RFC 6979 nonces. RSA-PSS uses our own EMSA-PSS with a salt derived from the seed. OpenSSL (`verify -x509_strict`, `cms -verify`), PKI.js and WebCrypto all accept the result.
   - Because of this, `@peculiar/x509` is not a dependency.
2. **No decorator syntax.** The `LDSSecurityObject` schema calls the `@peculiar/asn1-schema` decorators as plain functions: `AsnProp(opts)(Class.prototype, 'field')`.
   - This registers the same schema with no `@` syntax, so `erasableSyntaxOnly` holds and Node can run the files with type stripping. `scripts/gen-demo.ts` runs under plain `node`.
   - The sandbox printed `DGH der 300802010f0403010203` and parsed it back. The exception in IMPLEMENTATION 4.2 for decorators is therefore not needed.
3. **RSA keys come from our own seeded prime search**: an HKDF candidate, a small-prime sieve, then Miller-Rabin with fixed bases. Neither WebCrypto nor Node can seed RSA key generation. `build/tmp/1.8/rsatime.ts` measured RSA-2048 key generation at 95 to 200 ms.
4. **Size choices**: the RSA-PSS CSCA is 3072-bit and the DS is 2048-bit. The RSA AA key is 2048-bit with SHA-256. The BSI sample that task 1.9 uses is 1024-bit with SHA-1, so together the two exercise both branches.

## Known gaps

- Real CSCAs often use explicit EC domain parameters. The fixtures use named curves, because WebCrypto and PKI.js cannot import explicit parameters.
- `parseSod` uses asn1js 3 with no depth or size limits. It is a fixture and test parser, not the production parser (that is task 1.9).
- pnpm reports an unmet peer: `@li0ard/tsemrtd` wants `typescript ^5.9.3` and the repo has 7.0.2. It is a dev dependency used for its JavaScript build only, and it is harmless.
- No signingTime signed attribute (it is optional in Part 10).
- The RSA AA chip returns sigma as is, never n - sigma. A verifier should still handle both, as the research notes say.
