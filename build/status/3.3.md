## Design
- `verify(input)` = account_info (`readOpsState`, first ledger call), lookup, `BarVerification` hybrid-signed, stored. `issue(ops)` = 0a, 0b, credential row, `bar.verified` event. `onboard` = both. Every step first asks the ledger or the DB what is done, so rerunning is the resume.
- The pg-boss job holds only the operations account (no bar number, no salt). It retries (backoff) until 0b is accepted.
- Credential create/accept hashes are recovered from the ledger alone (entry `PreviousTxnID` is the accept; that transaction's `ModifiedNode.PreviousTxnID` is the create), so a crash between accept and the DB row loses nothing (tested).
- Step 0b is signed by the lawyer's operations key via an injected `opsAccept`; without it the result is `awaiting_ops_accept`.
- `link`: checks the bar number hash, opens `LC` with the salt, signs `BarDealLink`, self-checks with `verifyBarDealLink` (with opening), stores, zeroes the salt in `finally`. Same deal, role and verification returns the stored link.
- Every signature also writes an outbox event `verifier.signed`. The demo adapter's `source.url` is the registry root, never the lawyer's URL, so the bar number is not in a signed record.
- Enrollment list: hybrid-signed attest envelope, anchored by an `AccountSet` memo (`legx/enrollment-list/v1`, SHA-256 of the exact bytes) from the firm account; `checkEnrollmentList` checks signature, account and memo; served at `/.well-known/legx/enrollment-keys.json`.
