## Research notes
- Reliable submission: final only from a validated ledger; a missing transaction is final only past LastLedgerSequence with continuous history; the same blob is safe to resubmit; reconcile with `account_tx` by sequence. https://xrpl.org/docs/concepts/transactions/reliable-transaction-submission
- Malleability: a multisigned copy can validate under another hash; watch the Sequence. https://xrpl.org/docs/concepts/transactions/finality-of-results/transaction-malleability
- Result classes: everything from `submit` is provisional; tef "may already have been applied". https://xrpl.org/docs/references/protocol/transactions/transaction-results and .../tef-codes
- `tx`: `min_ledger`/`max_ledger` at most 1000 apart (`excessiveLgrRange`, measured); `searched_all` only advisory. https://xrpl.org/docs/references/http-websocket-apis/public-api-methods/transaction-methods/tx
- `account_tx` binary v2 entries carry `tx_blob`, `meta_blob`, `ledger_index` and `validated`, but **no hash** (measured), so the hash is computed with `hashes.hashSignedTx`. Entries inside a page may be unordered; pages are ordered. https://xrpl.org/docs/references/http-websocket-apis/public-api-methods/account-methods/account_tx
- Partial payments: `delivered_amount`. https://xrpl.org/docs/concepts/payment-types/partial-payments
- xrpl.js 5.3.0 (read in node_modules): it reconnects by itself after an unexpected close; dropped sockets give `ConnectionError` subclasses. All sources are in `packages/xrpl/SOURCES.md`.

## Evidence (xrpld 3.4.1 standalone; scripts in `build/tmp/2.2/`)
- `probe.ts`: resubmitting a blob that is **in the open ledger** gives `tefPAST_SEQ`, and so does **one that is already validated**. So "tef means not applied" would let money move twice, and the slot (account + sequence) decides every slot-type tef. Standalone `tx` over a fully covered range returns `searched_all: false`, so `searched_all` is unusable here as well as on Testnet. `delivered_amount` is absent on a tec Payment. In API v2, `date` sits inside `tx_json`, not at the top level.
- `gap.ts`: a held (terPRE_SEQ) transaction is answered by `tx` with min/max as `{hash, validated:false}`, **not** `txnNotFound`. A literal reading of "txnNotFound only" never expires it. Rule used: only a validated `tx` answer counts as found (pinned by a unit test). This caused one real-ledger failure before the fix.
- `fault.ts`: (1) xrpl.js passes through the raw `ws` error "WebSocket is not open: readyState 0 (CONNECTING)" during its own reconnect. It is not a `ConnectionError`, so `rpcOf` now wraps it as one (unit test). (2) xrpl.js `disconnect()` can hang forever when called while the socket is closing: its close handler runs `removeAllListeners()` and drops the resolver (seen 1 run in 40). `submitReliable` never calls `disconnect`; the tests use `disconnectQuietly`. (3) fast-check `scheduleFunction` runs the function at call time and schedules only the result, so kills use `s.schedule(...).then(kill)`.
- `meta.ts`, `txkeys.ts`: metadata blobs decode and encode with `xrpl.decode`/`encode`; v2 `tx` keys.

## How it decides (summary)
Slot = account + Sequence, or account + TicketSequence. At each validated ledger V: `account_info` (and the Ticket `ledger_entry`) says whether the slot is used. If it is, `account_tx` (binary) is walked back to the transaction in the slot. If that transaction equals ours without its signature fields, we return its validated result and hash (this covers malleated copies). Otherwise we return `rejected tefPAST_SEQ` or `tefNO_TICKET`. The walk says "nothing there" only when it provably reaches back before the slot (a lower Sequence sent by the account, or the account's creation). Otherwise it throws `NotFinalError`. A tem or non-slot tef is `rejected` only if the slot is also unused in the open ledger. `expired` needs all of: V > LastLedgerSequence, `complete_ledgers` covers minLedger..LastLedgerSequence, no validated `tx` answer over that range, and the slot unused at V. A timeout throws `NotFinalError`, never a failure. Timeouts use `performance.now()` (operational only, not a ledger decision).

## Design questions
- **DQ-2.2a (T-A-14 wording).** "Resubmit an old blob gives tefPAST_SEQ" holds for the raw engine result. `submitReliable` on a blob that already validated returns that original validation (same hash, same ledger), not `rejected`, because the slot shows our transaction applied. Saying "rejected" there would invite a rebuild on a new sequence and a second payment. A blob whose slot another transaction used is `rejected tefPAST_SEQ`. Please confirm.
- **DQ-2.2b (result shape).** P2.2-03 and T-A-15 write `{final:true, applied:false}` and `{expired:true}`. I followed the frozen contract `SubmitResult` (`validated` / `rejected` / `expired`), per 1.2's request.
- **DQ-2.2c.** Non-slot tef codes such as `tefBAD_AUTH` and `tefBAD_QUORUM` are treated as final for this blob, as the task says. In theory they could pass later if the signer list changed; the deal wallet's signer list is locked by design.

## Known gaps
- One trusted server is assumed: a lying server can still fool every check. Cross-checking two servers is not built.
- A blob without LastLedgerSequence can never be `expired`; it ends in `validated`, `rejected` or `NotFinalError`.
- Testnet was not exercised by this task (standalone only); the Testnet `searched_all` fact comes from IMPLEMENTATION 4.5.
- Ticket history walks rely on the stop rules above. A busy account with a long history pays for one `account_tx` page per 200 transactions.
