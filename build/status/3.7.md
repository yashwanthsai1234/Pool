## Design
- `compose.ts` `buildServer(deps)`: one Fastify with a raw-buffer JSON parser; mounts coordinator `register` (last, its wildcard answers the rest), FROST relay `register`, recovery agent `register` (root) and firm co-signer `register` (`/firm`, demo only), the routes in `routes.ts`, the WebSocket at `/ws`. Hooks: `onRequest` refuses a request with no `x-legx-auth` (except `/health`, `/ws`), `onSend` sets CSP (`frame-ancestors 'none'`), nosniff, no-referrer, no-store.
- `config.ts`: `assertProfile` is the only place that decides profile rules (demo port, `LEGX_DEMO_*`, ZK dev mode, Sepolia, mock identifier, agents in process). `main.ts` runs it before any connection.
- `live.ts` `LiveHub`: per socket one coalescing `serial` pump (replay and live are one path), listener added before the first pump, rows read from the table in pages, a row that is not `last + 1` is held back (`gapWaitMs`), send queue bounded by `maxQueue` unflushed messages (the pump waits for room; a socket that stalls for `stallMs` gets 4408), NOTIFY only wakes pumps, plus a fallback poll. `pgSource.ts`: dedicated LISTEN connection with reconnect (wakes everything after a reconnect).
- WebSocket auth: signed GET `/ws` (path `/ws` alone), header or `?auth=`; a socket reads a deal only if its enrollment key is pinned to that deal (`canRead`), else close 4403.
- `evidence.ts`: `dealRegistry` (coordinator key ids + service key), `composeEvidence` = `resilientSigner`, `hybridCheckpointLog`, `createLogService`, `registerCheckpointJob` (what 3.12 asked of 3.7).
- `demo.ts`: ports for the demo profile (all marked `demo: true`); `agents.ts`: demo agent deps. `renewal` (3.12) is NOT composed (gap 4).

## Design questions
- DQ-3.7-1: `GET /health` is unsigned (the contract says signed by `enrolled` or `operator`). A liveness probe or `pnpm dev` cannot sign. It lists impl names and status only, no secrets. Say if it must be signed.
- DQ-3.7-2: `ledger.validated` is pushed as `{type:'ledger', topic, payload}` (the OD-9 payload) because the contract union has no such variant (I-3.7-b).
- DQ-3.7-3: the signed path of the WebSocket upgrade is `/ws` without the `auth` parameter (I-3.7-c).

## Known gaps
1. ZK verify does not go through the composed server: `zk.verify` (and `bar.dealLink`, `bar.manualEvidence`, `keys.register`) authenticate and then answer 501, because the contract input is too small (I-3.7-d). The ZK adapter is composed and its config is checked at start (`createZkAdapter`), health reports it, but `verifyAndStore` is not reachable over HTTP.
2. Production wiring is not built: `main.ts` in the production profile refuses demo settings, then stops with "not wired in this build" (KMS signer, S3 store, Tessera log, real registry, release gate 1.12).
3. The recovery agent and the firm co-signer run mounted (demo) only; there is no separate-process entry point yet.
4. `@legx/renewal` jobs and the checkpoint cron are not started by `main.ts` (`composeEvidence` accepts `jobs` and registers the cron; main passes none). The evidence log is not fed by the coordinator (I-3.7-h).
5. The watcher in `main.ts` watches only the issuer account and has no evidence sink (I-3.7-g).
6. The routes sit at the root; the web app's `API_BASE` is `/api` and signs the path as sent, so a proxy that strips `/api` breaks signatures (DQ-4.1a). Decide before 4.3.
7. Single process: the hub keeps sockets in memory (one map from deal id to sockets, as designed); NOTIFY reaches every process, so several processes work, but the in-memory `lastLedgerId` is per process.
8. Not run: load test above 3 clients; the real 100/s load used one publisher process.
