## Research notes

- **KMS** (all in `signer/SOURCES.md`): Ed25519 is key spec `ECC_NIST_EDWARDS25519`, algorithm `ED25519_SHA_512`, MessageType `RAW` only (`ED25519_PH_SHA_512` is a different, non-interchangeable algorithm). RAW is limited to 4096 bytes and Ed25519 has no `EXTERNAL_MU`. So a PAE over 4096 bytes cannot be signed by KMS Ed25519, and `KmsSigner` refuses it up front. ML-DSA uses `ML_DSA_SHAKE_256` with `EXTERNAL_MU` (exactly 64 bytes). `GetPublicKey` returns an SPKI: 12-byte prefix plus 32 bytes (Ed25519), 22-byte prefix plus 1952 bytes (ML-DSA-65). Both are checked on parse.
- **mu** comes from `muFor` in `@legx/core/pq` (task 1.16). The KMS emulator signs with noble `ml_dsa65.internal.sign(mu, sk, { externalMu: true })` and the result verifies under Node's and noble's ML-DSA with the context, which cross-checks `muFor`.
- **LocalStack and ML_DSA_65:** the LocalStack KMS docs do not mention ML_DSA, ECC_NIST_EDWARDS25519 or EXTERNAL_MU, and no LocalStack issue discusses them. Floci (another emulator) added ML-DSA in PR 3047 with RAW only. So there is no emulator that models EXTERNAL_MU; KmsSigner is tested against a purpose-built emulator in `signer/test/helpers/fakeKms.ts`, which enforces the documented rules. It is NOT a recording of real KMS and has not been run against real AWS (no credentials here).
- **Tessera POSIX:** the conformance binary's `POST /add` reads the whole body as one entry, blocks until the entry has an index and answers with the decimal index (no newline), 500 on error. Read side is plain files: `/checkpoint`, `/tile/...`. Tile paths use `x`-prefixed 3-digit groups, partial tiles `.p/<W>`, tile height 8, and partial tiles may be deleted once the full tile exists (the adapter falls back to the full tile). The adapter waits for a checkpoint that covers the new index before `add` returns.
- **S3:** a versioned Object Lock bucket turns a plain `DeleteObject` into a delete marker, so `delete` deletes the specific version, which is refused before the retention date. Uses `If-None-Match: *` and a SHA-256 checksum on upload.
- **MinIO:** official `minio/minio` and `quay.io/minio/minio` could not be pulled (Docker Hub repository missing, Quay 401). Used `pgsty/minio:latest` (MinIO RELEASE.2026-08-04, community build).
- **OTel:** `@opentelemetry/sdk-trace-base` 2.12.0 is deprecated for `@opentelemetry/sdk-trace` (same version, new API: `TracerProvider`, processors take `{ exporter }`). Used `sdk-trace`. Versions: sdk-node 0.223.0, auto-instrumentations-node 0.81.0, api 1.9.1, sdk-trace/core/resources 2.12.0, exporter-trace-otlp-http 0.223.0, pino 10.4.0, client-kms and client-s3 3.1149.0 (3.1157 is too new for the 14-day rule).

## Evidence (deviations and findings from experiments)

- **Collector `hmac_key`.** DESIGN 8.6's processor block does not run on the current contrib image: `Error: invalid configuration: processors::redaction: hmac_key must not be empty when hash_function is "hmac-sha256"`, then, with a short key, `hmac_key must be at least 32 bytes long`. The shipped config adds `hmac_key: "${env:LEGX_REDACTION_HMAC_KEY}"` (an env var of at least 32 bytes). See Design questions.
- **MinIO delete refusal** answers `400 InvalidRequest: Object is WORM protected and cannot be overwritten`, while AWS answers `403 AccessDenied`. `delete` maps both to `retained`.
- **Extra blocked patterns.** `allowlist.ts` adds three value patterns to the DESIGN 8.6 list (hex of 64+ bytes, base64 of 90+ bytes, a PEM header), because DG1 bytes and keys travel as hex or base64, which the MRZ patterns cannot see. The Collector config carries them too.

## Design questions

1. **DQ-3.6-1 (Collector config).** DESIGN 8.6 shows `hash_function: hmac-sha256` without a key; the current Collector refuses to start without a 32-byte `hmac_key`. Suggest adding `hmac_key: "${env:...}"` to the DESIGN snippet and listing the secret in the deployment runbook.
2. **DQ-3.6-2 (Tessera and the 0x06 line).** Tessera signs its own checkpoint (Ed25519). Who adds the timestamped ML-DSA-44 cosignature (0x06) to a Tessera checkpoint? The adapter returns whatever note the sidecar serves; the contract test uses a fake that serves a hybrid note. A cosigning step (a witness-style service using `CheckpointSignerPort`, or a Tessera `AppendOptions` signer) must exist before production. Not decided here.
3. **DQ-3.6-3 (Ed25519 and large PAE).** KMS Ed25519 cannot sign more than 4096 bytes and has no EXTERNAL_MU, so the hybrid signer refuses a larger PAE. Events and attestations are far smaller today (DSSE payload cap 64 KB in contracts is larger than 4096, so a cap of about 3.5 KB on signed payloads, or a pre-hash step, is needed for the KMS profile). Which one is decided by task 3.4.
4. **DQ-3.6-4 (32-byte secrets in free text).** Value-level masking cannot tell a 32-byte salt or seed from a 32-byte hash, so a secret printed inside a message string is not caught; only the key-name rules (contract `Secret<>` leaves plus a static list) and the byte-array rule apply. Mitigation is the `Secret<>` brand and review.
