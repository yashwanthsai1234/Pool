## Design of the code
- `evidence.ts`: one internal `signAs`/`verifyAs` with the payload type as parameter; `signEnvelope`/`verifyEnvelope` (event), `signAttestation`/`verifyAttestationEnvelope` (attest); strict Ed25519 (`zip215:false`), canonical base64 (`fromBase64Strict` from pq.ts), chain via `entryLink` + `verifyChainWith(entries, check)`; `verifyChain(entries, keyFor, type?)` keeps the old signature. Hybrid chains pass `env => verifyHybrid(env, registry, at).ok` to `verifyChainWith`.
- `merkle.ts`: `consistencyProof`, `verifyConsistency` (RFC 9162 2.1.4). `mth`, `inclusionPath`, `verifyInclusion` stay in dealcore.ts.
- `checkpoint.ts`: `createLog(signing)` (in-process `TransparencyLogPort`, duplicate leaf returns first index, calls 1.16 `signCheckpoint`), `verifyReceipt` (offline inclusion receipt against a hybrid checkpoint).
- `clientRecords.ts`: `verifyClientRecords(records, check, { ledgerIndexOf, start? })`; `check` is an injected envelope verifier (not a keys map) so hybrid and classical both work.
- `machine.ts`: `transition` is total (returns `{ok, deal}` or `{ok:false, refusal:'illegal'|'quorum'|'gate'}`); `step` throws. `RELEASE_ESCROW` is `{gatePassed, submitter, releaser}` (orchestrator decision, DESIGN D4, D22, 6.17): refused with `gate` unless `gatePassed === true`, and with `submitter` unless submitter equals a non-empty releaser; no quorum. Other `sigs` events keep the 4-of-4 rule after the lock. T-P-04: I2 applies to wallet outflows only; I8 asserts gate and submitter.

## Research notes
- DSSE PAE: https://github.com/secure-systems-lab/dsse/blob/master/protocol.md ; cross-check `@sigstore/core@3.2.0` `dsse.preAuthEncoding` (added as devDependency of @legx/core), 300 random cases agree.
- C2SP: https://c2sp.org/signed-note (signature line is U+2014, space, name, space, base64(4-byte key ID || sig); notes need blank line before signatures; unknown keys ignored; must accept 16 lines) and https://c2sp.org/tlog-checkpoint (origin, decimal size, base64 root, optional extension lines). Signing and the 0x06 line are task 1.16's `pqCheckpoint.ts`; I call it.
- RFC 9162 2.1.4.2: https://www.rfc-editor.org/rfc/rfc9162#section-2.1.4. The transparency-dev vectors refuse size 0 (`size1-is-zero...`, `sizes-are-equal-zero...`), so `verifyConsistency` returns false for size1 < 1 (the RFC text does not say; the vectors do).
- Observation (not a bug): a consistency or inclusion proof verified with a different claimed size can still pass if the proof hashes happen to describe a valid tree; the size is bound only by the signed checkpoint. So the tests do not assert "wrong size fails"; callers must take the size from a verified checkpoint (`verifyReceipt` does).
