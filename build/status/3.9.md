## Design
- Wire (`frost/schema.ts`): a message is a contracts `FrostSignedMessage`; both signatures cover core's `frostMsgBytes`, so the Ed25519 half is the core `FrostMsg.sig` and 1.15's round functions run unchanged. Non-core kinds sign `sha256(payload)`. ML-DSA context `legx/dsse/v1`. Participants verify both halves (the relay is untrusted).
- Relay (`relay.ts`, `store.ts`, `routes.ts`): Postgres queue (two tables, `create table if not exists`), checks session, kind, sender's pinned `enrollment_key` row, both signatures, round order, duplicates; never imports signing, share or nonce code (tested). A signing attempt has a deadline; the first read or send after it closes the attempt and opens a new session for the next pair (fresh commitments). `GET /frost/sessions/:id/status` is extra.
- Agent: share only for client slots, AES-256-GCM vault with (deal, slot, epoch, key) as AAD, one row per slot; signs only an exit that the sealed deal allows (`cosign`), only after an authorized recovery (72 h, not cancelled), only for a pinned client holder, nonce marked in `frost_nonce_use` before release, `frost.signed` on aggregate, `frost.refused` on each refusal; repairs only toward the recovery's new key; refresh is `pending_deletions` until all deletion statements are in.

## Design questions
- DQ-3.9-1: ML-DSA context for relay messages reuses `legx/dsse/v1` (MlDsaContext has no frost context).
- DQ-3.9-2: `frost.signed` carries the aggregate, which the agent knows only after the other signer's share arrives (it aggregates itself via the relay). A released share without an aggregate leaves only `frost.refused`/no event; the agent should also log a `frost.share.released` kind.
- DQ-3.9-3: recovery events (`frost.recovery.requested/cancelled/authorized`, `frost.refused`) are not in `EventKind`.
- DQ-3.9-4: after DKG or refresh round 3 a holder waits `complaintWindowMs` for a complaint or abort; a holder that is late can still be left out, so test-signing (P3.9-18) is the real confirmation.
