## Research notes

- **Zod 4.6.7** (released 12 Oct 2026). `z.toJSONSchema` targets draft 2020-12, emits `additionalProperties: false` for strict objects, copies `.meta()` keys (so `x-legx-secret` shows up), skips refinements, and throws on unrepresentable types by default (none are used). `.brand()` is type-only and returns the same schema. Sources: https://zod.dev/json-schema, https://zod.dev/api?id=branded-types.
- **oRPC `@orpc/contract` 1.16.0** fits Zod 4. Its `Schema` type is `StandardSchemaV1` (read in `dist/shared/contract.*.d.mts`), and Zod 4 schemas expose `~standard` (vendor `zod`, version 1). `oc.$meta<{ auth?: AuthRule }>({})` plus `.meta()` gives a typed auth rule per route; `.route({ method, path })` holds the HTTP shape. Sources: https://orpc.dev/docs/contract-first/define-contract, https://orpc.dev/docs/metadata, https://github.com/standard-schema/standard-schema.
- **Version.** 1.16.0 was used, not 1.16.1. 1.16.1 (22 Oct) is younger than the workspace's 3-day minimum release age; 1.16.0 (21 Oct) passes it. Both are under the 14-day rule in IMPLEMENTATION 4. Reason: IMPLEMENTATION pins 1.16.x.
- **ZKPassport result shape** (read from `@zkpassport/sdk` 0.19.2 typings and the 24 Oct prototype logs in the research scratchpad): the identifier is a decimal string; `uniqueIdentifierType` is the numeric `NullifierType` (0 NON_SALTED, 1 SALTED, 2 NON_SALTED_MOCK, 3 SALTED_MOCK, 4 NONE); `vkeyHash` is `0x` plus 64 lowercase hex; `version` looks like `0.21.1`; `queryResultErrors` is nested category, then check, then `{expected, received, message}`.
- **noble FROST** (`@noble/curves` 2.4.0 `abstract/frost.d.ts`): identifiers are hex scalars; DKG round 1 has commitment points and a 64-byte proof of knowledge; round 2 carries `signingShare` (so it is sealed in our contract); nonce commitments are `{identifier, hiding, binding}`.

## Decisions that later lanes should know

- The live-update file is `ws.ts`, not `sse.ts`: the transport is WebSocket (IMPLEMENTATION 3.7, 4.7).
- **Naming.** Signed records and events use snake_case, as DESIGN writes them. `PublicDealData`, ports and API wrappers use camelCase.
- **Hex.** Internal hashes are lowercase; XRPL hashes and keys are uppercase; Ed25519 signatures in records are lowercase hex; ML-DSA material is base64.
- **`sig_algs`** is inside every signed payload: event predicates and all attestation payloads (DQ-1.2b).
- **Events.** Each event's predicate has a per-kind `data` object. DESIGN 8.1 lists what 13 kinds record; the shapes of the other 14 are this task's design.
- **Party actions** reach the coordinator as signed events (`events.append`). The coordinator applies the event, the state change and the outbox row in one transaction.
- **ZK privacy.** `ZkVerification.committedInputs` keeps only `custom_data`, and `queryResultErrors` keeps only messages, so no disclosed fact ends up in a stored result. `ZkVerifyRequest.queryResult` is Secret.
- **Secret inputs.** Only three route inputs take Secret fields: `bar.verify.barNumber`, `bar.dealLink.barSalt` and `zk.verify.request.queryResult`. No response, event, record or relay message does; a test enforces this.
- **Holder roles** match DESIGN 6.4 and the encoding rules: `phone`, `second-authenticator`, `recovery-agent`, `console`, `firm-hsm`, `partner`, plus `passkey-same-device` for the labeled single-device mode that `@legx/core/frost` uses. `security-key` and `second-device` are gone.

## Design questions

All six were decided by the orchestrator (DESIGN.md updated) and applied; the `it.todo` markers are removed.

- **DQ-1.2a, gate onboarding check.** `ONBOARDING_OK` trusts the client's own lawyer's onboarding attestation, which states `C_side` (DESIGN 6.17). No contract change was needed; `IdentityOnboarded` already carries `commitment` and `unique_identifier`.
- **DQ-1.2b, `sig_algs` in attestation payloads.** Confirmed.
- **DQ-1.2c, checkpoint signing.** Added `CheckpointSignerPort`: Ed25519 over the note body (0x01) and ML-DSA-44 over the CosignedSubtree with the empty context (0x06), returned together (DESIGN 6.13). `SignerPort` is unchanged.
- **DQ-1.2d, FROST slot signers.** They are not `SignerPort`; they use FROST sessions from `@legx/core/frost`.
- **DQ-1.2e, API auth.** Every route is now a signed request (`AuthRule.kind = 'signed-request'`) with its allowed callers. The `x-legx-auth` header (`ApiAuth`) holds a 32-byte nonce, the ledger index, and hybrid signatures by pinned enrollment keys. The signed message is `tupleHash("legx/api-request/v1", [utf8(method), utf8(path), SHA-256(body), nonce32, uint32_be(ledgerIndex)])`. The server refuses a reused nonce and a ledger index more than 20 ledgers old (DESIGN 8.10). The records routes add `ownSideOnly`.
- **DQ-1.2f, FROST complaint.** `dkg.complaint` now carries the accused's signed round-2 message (ciphertext included) and `decrypted_share`; anyone checks it against the sender's Feldman commitments, and the DKG aborts and restarts (DESIGN 6.4 rule 3).

Changes that came with these decisions:
- `records.list` and `records.bundle` take `{ dealId, side }` only; the nonce and ledger index moved into the header.
- `recovery.cancel` now takes `dealId`.
- `recovery.start` for a lawyer carries `opsSig`, the operations account's signature over the same api-request message (DESIGN 6.4).
- `bar.record`, `keys.get` and `health` are signed too (callers `enrolled`, or `operator` for health).
- **Remaining open point:** DESIGN does not name the ML-DSA context for API request signatures. I propose `legx/api-request/v1` (the tag), for task 1.16 to confirm.
- **`BarVerification.status`:** DESIGN shows only `"active"`; the contract also allows `not_active`, so a failed check can be signed and recorded.

## Changes requested by task 1.15 (applied)

- `dkg.round1` carries `kem_pub`, a fresh per-session X-Wing public key (1,216 bytes, base64). Round-2 shares are sealed to it.
- `dkg.complaint` carries `kem_secret` (the complainant's 32-byte X-Wing seed for that session) next to `decrypted_share`. Anyone can open the accused's signed ciphertext and run the Feldman check; the DKG aborts and restarts.
- `repair.delta` carries `delta_commitments` (`D_ij = delta_ij * G` for both helpers), so a cheating helper can be named. The new `repair.sigma` kind carries the helper's sigma, sealed to the new holder.
- `cosign` needed a user-verified approval for `second-authenticator` as well as `firm-hsm`. `sign.request.approval` already carries it (a superset of core's `Approval`); only its comment changed.
- The relay review test lists the reviewed clear fields: `kem_secret` and `decrypted_share` (complaint only) and `share` (a public signature share). Any other secret-like field fails.
- Sizes were measured with noble `ml_kem768_x25519` 0.7.1: public key 1,216 bytes, secret key 32 bytes.

## Requests to other tasks

- **3.2 and 3.7:** every route now verifies `SHA-256(raw body)`. So the server needs the raw body for every route, not only the records view: either a Fastify hook that verifies before the oRPC handler, or plain Fastify routes.

- **2.2:** `SubmitResult` is discriminated by `status` (`validated`, `rejected`, `expired`). It replaces the ad hoc shapes in the P2.2 rows.
- **3.11:** the adapter must:
  - write `0x` lowercase hex;
  - map numeric `NullifierType` values to their names;
  - keep only `custom_data` in `committedInputs` and only messages in `queryResultErrors`;
  - record `scope` and `domain`.
- **3.6:** build pino `redact` paths with `secretPaths(schema)`, and a Biome or lint rule against logging `Secret<>` values.
- **1.15:** FROST identifiers in messages are noble `Identifier` hex. Round-2, refresh and repair shares go only in a `SealedBox`.

## Known gaps

- An object with a throwing getter makes Zod throw its own error, not a `ZodError` (pinned in `test/fuzz.test.ts`). Every boundary must parse `JSON.parse` output, never a live object.
- Address checks cover the format and the checksum only; deriving an address from a public key stays in core (`verifyXrplKeySig`, `deriveAddress`).
- The per-kind event `data` shapes for kinds DESIGN does not detail, and the route list, are this task's design and need the lane owners' review at the freeze.
