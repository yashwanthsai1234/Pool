## Design (summary)
`WatcherClient({servers, accounts, cursorStore, handler, onAlert?, pollMs?, pageLimit?})`, `start()`, `sync()`, `idle()`, `stop()`. `servers` are `Link`s (`xrplLink(name, url)` wraps xrpl.js via `rpcOf`; tests use a model `FakeLink`). servers[0] is the primary and feeds the handler; the others are only compared. All work runs on one FIFO queue. Stream `transaction` messages with `validated:true` go to the handler (fast path); every `ledger` message and every tick (default 5 s) runs a sync: `account_tx` forward from cursor+1 to the validated head, following `marker`, whole ledgers handed over in (ledger_index, TransactionIndex) order, cursor moved after each complete ledger. `up` (xrpl.js reconnected) forces subscribe then backfill. Dedup on hash in memory (pruned below the lowest cursor); the DB handler must still be idempotent on `tx_hash` (crash between handler and cursor replays the ledger). Comparison: after each sync, hash of the newest ledger both servers have (a hash covers its parent, so one match proves all earlier history).

## Research notes / evidence
- Sources are in `packages/xrpl/SOURCES.md` (2.7 section). Probe: `build/tmp/2.7/probe.ts` on xrpld 3.4.1 standalone: stream messages carry `validated:true`, `hash`, `ledger_index`, `meta.TransactionIndex`, `tx_json` (API v2); `account_tx` with `ledger_index_min` below the earliest ledger fails with `lgrIdxMalformed`, `-1` works; the `ledger` stream message can arrive before the transaction messages of the same ledger, so either path may deliver first (both dedupe).
- 2.2 quirks reused: `rpcOf` (raw socket errors become ConnectionError); `close()` races `disconnect()` against 3 s because xrpl.js can hang. xrpl.js reconnects by itself; the `connected` event is our `up`.

## Known gaps
- Only servers[0] feeds the handler; there is no automatic failover to another server.
- Disagreement is detected on the newest common validated ledger; Testnet (`s.altnet` vs Clio) was not exercised (standalone only).
- A backfill holds at most one page plus one ledger in memory, but a very long outage means many sequential `account_tx` pages per account.
