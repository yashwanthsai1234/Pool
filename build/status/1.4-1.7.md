## T-U-06: why the golden values are new
The starting-code seal (Appendix A) hashed 13 fields (`contractHash`, x-keys, commitments, lawyer keys, signer accounts, quorum, payouts). DESIGN 6.6 now defines 29 fields: it adds `signedContractSeal`, `walletAddress`, `idMethodA`/`B`, `identityPolicy`, the three ops/releaser accounts, four slot policies and four `pqKeyHash` values.

## Research notes
- **rippled key checks.** rippled `PublicKey.cpp` reads a key as Ed25519 when it is 33 bytes with `0xED` first, and as secp256k1 when the first byte is `02` or `03`. It verifies secp256k1 over `sha512Half(m)` and requires a fully canonical (low-S) DER signature. For Ed25519 it requires S < L and verifies over the raw message. Source: https://github.com/XRPLF/rippled/blob/develop/src/libxrpl/protocol/PublicKey.cpp
- **noble-curves 2.4.0, read in `node_modules`.**
  - `ed25519.verify` defaults to `zip215: true`. With `zip215: false` it also rejects small-order A.
  - secp256k1 `verify` with `{prehash: false, format: 'der', lowS: true}` returns false and does not throw for a compact signature, a high S, an empty or oversized signature, or an off-curve key (sandbox `build/tmp/1.4-1.7/secp-probe.ts`). It throws only for argument types that are not `Uint8Array`.
  - Source: https://github.com/paulmillr/noble-curves
- **ZIP-215 universal forgery.** With the identity key (`01 00…00`, or its non-canonical form y = p+1), `(R = sB, s)` verifies under ZIP-215 for any message. T-U-20a and T-U-20b use this real attack, plus speccheck cases 0, 1, 9, 10 and 11 and all 196 entries of `zip215.json`. Sources: https://zips.z.cash/zip-0215, https://github.com/novifinancial/ed25519-speccheck
- **Node and noble differential.** Task 1.3 already recorded it in `vectors.test.ts`: on speccheck, Node accepts only case 3, so it is stricter than noble on cases 2, 4 and 5. Node never accepts a case we reject.
- **xrpl.js multi-signing message.** In ripple-binary-codec 2.11.0, `encodeForMultisigning` serializes only the signing fields, so `Signers` drops out, then appends the signer's AccountID.
- **Mint limits.**
  - NFTokenMint URI: at most 256 bytes, hex in JSON. Ours is 75 bytes.
  - `Memos`: at most 1 KB serialized. Ours is 225 bytes: F9, EA, 7C + 1 + 21, 7D + 2 + 195, E1, F1.
  - `MemoType` must use URL characters; `legx/contract-sigs/v1` does.
  - Sources: https://xrpl.org/docs/references/protocol/transactions/types/nftokenmint, https://xrpl.org/docs/references/protocol/transactions/common-fields
- **Which keys may sign.** `lsfDisableMaster` is `0x00100000`. `RegularKey` is the address of a key pair that may sign instead of the master key. The master key signs only while it is not disabled. Sources: https://xrpl.org/docs/references/protocol/ledger-data/ledger-entry-types/accountroot, https://xrpl.org/docs/concepts/accounts/cryptographic-keys

## API (for the lanes that consume it)
- `@legx/core/verify`:
  - `verifyXrplKeySig(pubHex, msg, sigHex): boolean`. It never throws on bad input; a wrong argument type throws a `TypeError`.
  - `verifyMultisigned(blob, expected)`. It returns `ok: false` on hostile blobs and has no signature code of its own.
- `@legx/core/signedContract`:
  - Message and signing: `contractSigMsg`, `signContract(sign, terms, role)` (async; it refuses a signature that does not verify strictly under the sealed key).
  - Building: `buildSignedContractSeal(terms, sigs) -> { seal, uriHex, memoHex }`, `nftUri`, `encodeMintMemo`, `decodeMintMemo`, `MINT_MEMO_TYPE`.
  - Checking: `verifySignedContract(terms, memoHex, uriHex) -> { ok: true } | { ok: false, code }`. The codes are `MEMO_MALFORMED`, `URI_MALFORMED`, `KEYS_NOT_SEALED`, `SIG_LA_INVALID`, `SIG_LB_INVALID` and `SEAL_MISMATCH`.
  - All hex is uppercase only (ledger hex rule).
- `@legx/core/dealcore`:
  - `dealSeal(d: PublicDealData)` throws on any input DESIGN 6.6 refuses.
  - `domain(root, seal)` returns 65 bytes.
  - `SEAL_FIELDS` is the 29 `[name, encoder]` pairs in DESIGN order.
- `@legx/core/opsBinding`:
  - `opsBindMsg(terms)`, `verifyOpsBinding(accountInfo, binding) -> { ok } | { ok: false, code }`.
  - The codes are `NOT_VALIDATED`, `ACCOUNT_MISMATCH`, `OPS_KEY_NOT_AUTHORIZED`, `OPS_SIG_INVALID` and `LAWYER_SIG_INVALID`.
  - `accountInfo` is the validated `account_info` result (`validated`, `account_data.{Account, Flags, RegularKey}`). The function does no network read.

## Known gaps
- **Hex case.** `decodeMintMemo` and the URI check accept uppercase hex only, which is the ledger rule and what rippled returns. A layer that lowercases `MemoData` would make the check fail closed.
- **Local role type.** `LawyerRole` (`'LA' | 'LB'`) is a local type in `signedContract.ts` and is reused by `opsBinding.ts`. `@legx/contracts` exports only the Zod value `LawyerSlot`, with no TypeScript type, and core does not depend on zod. It is structurally the same.
- **Wrong argument types.** P1.4-05 says "a typed error". The IMPLEMENTATION "Think" text says the function returns a boolean and never throws on bad input, so an unknown key type returns `false`. Only a wrong argument type throws, and it throws a `TypeError`.
